# Landing acceptance

Run only checks relevant to the requested page, and fix observed defects.

## Reading and evidence

- Does the first viewport identify the real offer, audience and next action?
- Are real work/results visible, rather than only abstract promises?
- Do course duration, schedule, support and access conditions agree across views?
- Are proof, role labels and quotations supported? Are demos labelled?
- Are chosen sources and adaptations explicit, without claiming unvisited pages
  were inspected or gallery assets are reusable?

## Layout and interaction

- Desktop, tablet and narrow phone: page-wide overflow, word wrapping, isolated
  syllables, overlapping text, obscured controls and usable touch targets.
- Media loads at correct aspect ratios, captions match it, and no private data
  appears in screenshots, scripts, JSON, source maps or public downloads.
- Navigation, day/plan switches, accordions, actual sample calculations, exports,
  contact links and clipboard normal/denied states work.
- Buttons have a meaningful destination/action and keyboard focus. Reduced motion
  does not hide content. Long pages retain ordinary scrolling.
- Observe motion rather than accepting a nonblank still. Test final/replay states
  and changing the sample while animation runs.

## Release

Publish only the reviewed static output or supported server bundle. Keep private
research and unrelated source files out. Preserve the Site/project identity.
For a public landing, verify unauthenticated access; for restricted sharing,
verify actual access control rather than an unlisted URL. A preview URL or
saved version is not a live deployment.

Report the actual live URL, useful source location and limits. Do not send an
application, book a meeting, change a portfolio or add tracking merely because
the user approved a landing-page build.
