# 디자인 시스템·접근성·설계 점검 적용 노트

아래 판단과 예시는 이 사용자용으로 새로 작성했다. 큐시트의 원문이나 원저자의 제작 방법을 인용한 것이 아니다.

## 토큰·이름

surface/text/action/status처럼 역할을 드러내는 이름을 프로젝트 언어로 정한다. 컴포넌트 이름이 구현과 실제 행동을 설명하도록 하고 중복 이름을 합친다.

## 상태·컴포넌트

기본/호버/포커스/선택/비활성/로딩/오류를 실제 필요한 컴포넌트에서 정의한다. 구조가 같은데 역할이 다른 컴포넌트를 무리하게 하나의 범용 요소로 합치지 않는다.

## 접근성·운영

표준의 현재 원문과 도구 측정을 함께 확인한다. 색 대비 도구는 전체 접근성을 검증하지 않는다. 키보드 경로·대체 텍스트·폼 설명을 조작해 확인하고, 도입 규칙은 현재 팀/개인의 규모에 맞춘다.

## 관찰을 결과물로 옮기기

참고한 화면의 URL과 관찰한 특징을 실제 변경에 연결한다. 예를 들어 “메뉴가 예쁨” 대신 “주요 이동과 보조 행동의 시각적 무게가 구분됨 → 현재 메뉴에서 핵심 행동을 한 단계 드러냄”처럼 설명한다. 관찰하지 않은 동작이나 보이지 않는 모바일 상태를 추측으로 채우지 않는다.

“버튼과 입력창 스타일 정리해줘” → 실제 사용하는 버튼·입력창의 의미와 상태를 묶고 토큰과 코드에 반영한다. 거대한 별도 문서 사이트를 먼저 만들지 않는다.

## 납품

프로젝트에 반영한 토큰/컴포넌트/간결한 사용 규칙, 확인한 상태와 남은 차이를 전달한다.

변경 파일·화면·출력과 확인 근거를 먼저 말한다. 미검증 상태를 짧게 밝히고, 요청이 끝났으면 형식적인 승인 질문을 붙이지 않는다.
